## 1. 专题：核心功能「降价提醒」的端到端断链

这是本次审查最需要优先处理的发现。产品定位里的「降价提醒」目前**从用户点按钮到收到微信消息，整条链路上有 6 处独立断点**，任何一处都足以让功能不可用：

```
用户点「开启微信提醒」
  │
  ① config/index.js:17  subscribeTemplateIds = []
  └─→ alert.js:247 直接 toast「尚未配置订阅消息模板」返回，授权根本没发起
        │
        ② server/.env 需手动补 OIL_SUBSCRIBE_TEMPLATE_ID
        │  未配 → subscribe.js:65-67 返回 TEMPLATE_NOT_CONFIGURED
        │
        ③ 即使配好，alert.js:97-102 的 data 是裸字符串
        │  微信 API 要求 {"thing1":{"value":"..."}} → 下发必被拒
        │  且 alert.js:185-191 会把失败记入 alert_logs，该事件永不再重试
        │
        ④ 规则匹配字段名对不上库表
        │  alert.js:108 读 rule.targetEnabled（schema.sql 无此列）
        │  alert.js:127 读 rule.forecastDrop（实际叫 predictDrop，dao:435）
        │  → 目标价 / 预测下调两个分支是死代码
        │
        ⑤ 官方降价分支依赖 latestOfficial()（dao:237 只查 approved）
        │  全库没有任何把 review_status 置为 approved 的路径 → 恒 null
        │
        ⑥ 前端 alert.js:255 把「一次性授权」永久存成 subscribeGranted=true
           服务端无额度消耗回写 → 发 1 条后额度耗尽，UI 仍显示「已开启」
```

**建议的最小可用路径**：先打通 ①②④⑤（配模板 ID → 字段名对齐 → 打通通知审核 → 补额度计数），再处理 ③⑥ 的格式与体验。第 ③ 条必须修，否则配好模板后每条消息都会静默失败并把事件锁死。

**退化预测**：把 `subscribeGranted` 从布尔改成「剩余可发次数」会同时牵动 `utils/store.js`、后端 `alert_rules` 表、`openapi.json` 的 `AlertRuleInput`、提醒页 WXML 四处；若不写迁移，存量 `true` 会被当成 0 次而全部停发。建议保留布尔字段做兼容，新增 `subscribeQuota` 计数列。

### P0 · 阻断级

#### P0-1 首页「最新调价通知」在真实后端下整体失真（字段契约漂移）

- **位置**：`pages/index/index.js:290`、`data/demo.js:213`、`server/src/services/query.js:179`、`utils/api.js:112`
- **依据**：演示源返回 `latestNotice`，后端返回 `notice`（另有 `changes` / `publishedAt`），前端只读 `latestNotice`。而 `getHome` 的 `expectKeys` 是 `['prices','window']`，不含通知字段，所以后端响应被判定成功并标为 `live`。
- **用户可见后果**：`latest = {}` → 通知卡片标题空白、日期 `--`、金额 `0.00`、文案「与上次持平」；`executeText` 渲染成「` 时执行。以下为本地各油品调整后的零售价格。」；点开的详情弹层四个油品价格全是 `0.00`、来源只剩「未标注来源」。另外后端 home 不返回 `updatedAt`，`index.js:350` 会拼出「` 更新」。
- **修复建议**：后端补 `latestNotice` 别名（兼容优先，改动面最小）并补 `updatedAt`；或前端统一改读 `notice` 并同步改演示源。`expectKeys` 补上通知 / `trend30` / `updatedAt`；字段缺失时渲染 `--`，不要把 `undefined` 交给 `changeMeta()` 变成 0。详情文案改用后端 `notice.summary`。**补一条端到端断言**：把 `/api/home` 的真实响应喂给 `applyHome()`，断言通知标题/金额非空。
- **退化预测**：只改一端会造成 demo / live 其中一路空白，必须两端同改并一起加断言。若靠「加严 `expectKeys` → 整体回落 demo」来兜底，会出现「后端有真实价格、只是没有通知」时整页切成演示数据，反而更误导；应改成字段级空态，而不是整包回落。

#### P0-2 通知复核队列只进不出，正式通知与官方降价提醒永不生效

- **位置**：`server/src/services/collector.js:74`、`sources.js:155`、`dao/index.js:212 / 237 / 244 / 269`、`schema.sql:58`
- **依据**：全库 `approved` 只出现在 `server/scripts/selftest.js:113` 的测试夹具里；生产代码、路由、schema、脚本中**没有任何 `UPDATE oil_notices` 或审核入口**。采集器写入的公告一律 `pending`，而 `listPublic` / `latestOfficial` / `latestByKind` 三个读接口一律 `WHERE review_status='approved'`。自检直接插 `approved` 数据，把这个断裂完全掩盖了。
- **用户可见后果**：`/api/notices` 的 `notices` 恒为 `[]`；`/api/home` 的 `notice` 恒 `null`、`changes` 恒 `{}`；`alert.run()` 的 `latestNotice` 恒 `null`。同时 `/api/sync-status` 可能仍报「同步正常」，出现「状态正常但列表全空」。
- **需线上核实**：请在生产库执行 `SELECT review_status, count(*) FROM oil_notices GROUP BY 1;`，确认运维是否曾手工置位。若已有 approved 数据，本条降级为「缺少可重复的审核流程」。
- **修复建议**：提供带独立鉴权的审核接口或运维脚本，逐条核对后写 `approved` 并修正 `changes`；或对已验证来源、且解析出完整分油品幅度的公告直接以 `approved` 入库。补断言「`collector.run()` 实际产出的公告能被 `listPublic` 查到」，**禁止测试直接插 approved 冒充**。
- **退化预测**：直接把采集结果默认改成 `approved` 会绕过 AGENTS.md「绝不把猜测值发布成正式结果」的硬约束 —— `sources.js:140-143` 在 `perFuel:false` 时仍会把同一总幅度复制给四个油品，复核人一键通过就等于发布猜测值。审核接口本身是新攻击面，必须用独立管理员凭据并记操作日志，不能复用用户 token。

#### P0-3 后端密钥可为空，可伪造任意 openid 越权

- **位置**：`server/src/config.js:54`（`optional('OIL_TOKEN_SECRET','')`）、`services/auth.js:103`、`src/index.js:11-19`、`app.js:30-32`、`.github/workflows/deploy-backend.yml:70-74`
- **依据**：`config.js` 定义了 `need()` 但全项目无人调用；`start()` 不校验任何配置；空串作 HMAC key 不报错，`issueToken` 照常签发。CI 首次创建 `.env` 时**只写 `DATABASE_URL`**，仅用一句 echo 提示手动补密钥；`/health` 既不查配置也不连库，服务带空密钥正常启动且健康检查返回 200。
- **风险**：算法在开源代码里，攻击者用空密钥即可自签任意 `openid` 的 token；`requireAuth` 只校验签名不查库，随后 `/api/rules`、`/api/history` 以该 openid 读写他人数据。**需核实线上 `server/.env` 是否确实配了该变量**（按约定不入库，本次无法读取）。
- **修复建议**：`start()` 启动时强校验 `tokenSecret`（长度 ≥ 32）、`appId`、`appSecret`、`databaseUrl`，缺一即打印错误并 `process.exit(1)`；`issueToken` 入口再断言一次；把配置状态纳入 `/health` 或独立 `/ready`；CI 健康检查改探 `/ready`。补一条「不设密钥时启动失败」的用例。
- **退化预测**：加启动校验会让 `server/scripts/selftest.js`、`check-openapi.js`、根目录 `scripts/check-modules.js` 这些不注入密钥的自检**立刻全部失败**，必须同步给自检脚本注入测试密钥或加显式测试开关，且该开关严禁出现在生产配置里。

### P1 · 严重 / 明确错误

#### P1-1 「空数据」被判为 live，`0.00 元` 冒充真实价格

- **位置**：`utils/api.js:49-55`（`hasExpected` 只判 `!== undefined && !== null`）、`utils/format.js:8-12`、`pages/global/global.js:85-90,113`、`pages/index/index.js:412-415`、`pages/alert/alert.js:77-82`
- **现象**：后端返回 `{points: []}` / `{prices: []}` / `{price: null}` 时字段都在、值为空，`hasExpected` 通过 → 标 `live` → 国际页顶部显示「行情实时」但曲线空白；`fmt.price(null)` 因 `Number(null)===0` 返回 `'0.00'`，提醒页显示「当前 **0.00** 元/升」、地区弹层显示「92# **0.00**」；首页 `prices` 为空时 `hero` 为 `undefined`，主价格整块空白。
- **修复**：`hasExpected` 对数组字段校验 `length > 0`，对价格字段校验 `isFinite(Number(v))`；`format.price()` 对 `null/undefined/''` 统一返回 `'--'`；国际页补 `points.length === 0` 的显式空态。
- **退化预测**：`price()` 改成 `--` 后，任何把价格文本再拿去 `Number()` 或 `.toFixed()` 的地方都会得到 `NaN`，需全仓 Grep 一遍调用点；建议同时提供 `priceValue()` 保留数值语义。

- **退化预测**：前端 `index.js:265-280` 的 `forecastKnown` 分支依赖 `forecast[fuelId]` 为数字，改结构后必须同步更新，否则会走「方向未定」或显示 `NaN`。

#### P1-6 非法 `regionCode` 静默回退默认地区，返回自相矛盾的数据

- **位置**：`server/src/shared/shared.js:941-946`（找不到返回 `REGIONS[0]` 上海）、`query.js:117/199`、`notices.js:15`、`dao/index.js:88-90`（用**原始** code 查库）

#### P1-7 `direction` 两态实现把「持平」显示成上涨

- **位置**：`server/src/services/query.js:261`、`notices.js:141`、`shared.js:187`；对照 `query.js:138` 的三态实现、`openapi.json:865-873`

- **修复**：统一 `v < 0 ? 'down' : v > 0 ? 'up' : 'flat'`，同步补 openapi 两处 enum。
- **退化预测**：前端 `global.js:80,87` 在无 `direction` 时用 `Number(changeAmount) < 0 ? 'down' : 'up'` 兜底，也要一并改成三态，否则 0 仍显示涨。

#### P1-8 生产库 `oil_adjust_events` 永远为空，走势页调价节点恒不显示

- **位置**：`dao/index.js:183-196`（`insertMany`）、`server/scripts/test-fixtures.js:60`（唯一调用点）、`query.js:42`、CI `deploy-backend.yml:88-91`（明确跳过演示数据灌入）
