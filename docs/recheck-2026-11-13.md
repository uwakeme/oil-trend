## 2. 阻断级问题（R0）

### R0-1 订阅消息 `data` 仍是扁平字符串，微信平台必拒 —— P0-4 未修

**这条是我亲自逐文件核实的，不是推断。**

- `server/src/services/alert.js:102-110`：`buildData()` 返回 `{thing5:'92# 汽油', amount2:'0.10元', phrase1:'下调', date3:'2026年11月24日', thing4:'...'}`，全是裸字符串。
- `alert.js:132-137`：原样传给 `subscribe.send({ data: templateData })`。
- `subscribe.js:73-82`：`body.data = options.data || {}`，无任何包装。
- `auth.js:36`：`JSON.stringify(post)` 直接发给微信。
- 全仓 Grep `server/src` 找不到任何 `value:` 包装。
- 微信 `message/subscribe/send` 要求 `{"thing5":{"value":"..."},...}`，扁平值会被以 47003 一类参数错误拒收。

**为什么自检全绿**：`subscribe-templates.js:121` 的 `validate()` 用 `var value = data[key]` 取扁平值校验长度/格式，`selftest.js` 又用同一份扁平契约表断言 —— 两边「一致地」漏掉了包装。我实测过：若只把 `buildData` 改成 `{value}` 包装，`validate()` 会立刻报 `TOO_LONG/[object Object]`、`BAD_DATE`，说明**校验与格式化必须一起改**。

**致命的组合效应**（配合 R1-5）：一旦配好模板 ID，第一批提醒**全部发送失败**；`alert.js:250` 会把失败回填进 `alert_logs` 并永久占住 `dedupKey`；之后即使修好格式，这些事件也不会重发。等于整条链被一次性锁死。

**修复**：
1. `buildData()` 输出 `{ [k]: { value: String(v) } }`；
2. `subscribe-templates.js:validate` 改为解包 `data[k].value` 再校验；
3. 补一条断言「最终 POST body 的 `data` 每个字段都是含 `value` 的对象」，用微信官方请求体的固定 JSON 夹具交叉校验，不要自查自己生成的契约表；
4. **清理线上已产生的失败占位行**（`DELETE FROM alert_logs WHERE sent=FALSE`），否则历史失败事件不会重发。

### R0-2 机器判定 `approved` 会把残缺/错误公告自动发布，人工关卡被取消

报告把 P0-2 标「部分」的理由只写了「ndrc 来源未启用」，没提语义变更本身。原硬约束是「解析不出结构化字段时进人工核对队列，**绝不把猜测值发布成正式结果**」；现在 `listPublic/latestOfficial` 只认字符串 `approved`，而 `approved` 由正则自动给出，`review-notices.js` 明说自己「不是审核入口」且全文只有 `SELECT` —— 发布前没有任何人工介入点，也没有下架/撤回能力。

**我跑了纯函数实测**（`sources.PARSERS.ndrcNotice`），四类错误输入全部被判 `approved`：

| 输入 | 输出 | 问题 |
| --- | --- | --- |
| 只写 `92号汽油每升下调0.10元` | `approved`，`deltas:{92:-0.1}` | 只有 1/4 个油品就发布 |
| `92号汽油、98号汽油每升下调0.10元` | `approved`，`deltas:{98:-0.1}` | 顿号串号歧义，92# 没幅度仍发布 |
| `92号汽油每升调整0.10元，0号柴油每升调整0.10元` | `approved`，`delta:+0.10`、全部 `+0.10` | 中性词「调整」被判**上涨** |
| `上次调价自2026年11月1日24时起，本轮92号…下调0.10元` | `approved`，`executeAt:'2026-11-01'` | 取到**上一轮**日期 |
| 正常四油品 | `approved` | 对照组 |

代码依据：`sources.js:159` `perFuel = Object.keys(deltas).length > 0`（只要 ≥1）；`:126/130/156` 方向词 `(上调|下调|调整)`，非「下调」一律取正；`:135` 日期正则不限语境。`collector.js` 的 `noticeSummary` 在 approved 分支还会写「逐项列明各油品调整幅度」——残缺公告配这句是反向错标。

另外 `collector.js:517-520` 对所有解析成功的通知（含 pending）返回 `status:'ok'`，pending 不进 `collector_runs.needsReview`，前端同步状态看不到存疑，只能人工连库跑脚本。

**修复**：
1. `perFuel` 收紧为四油品齐全；串号歧义（同一幅度前出现多个标号）直接判 pending；方向只认「上调/下调」，「调整」判 pending；日期要求紧邻「自…起」生效语义且不得早于上一轮窗口；`noticeSummary` 按实际 `changes` 数量生成。
2. 补独立发布态（如 `publish_status`）或给看板加「下架/置 pending」的写能力 + 审计日志，`listPublic` 同时过滤。
3. 让 pending 进入 `needsReview` 队列，前端可见。
4. 新增端到端用例：`collector.run()` 用 fixture 正文产出 → 断言入库 `review_status` → 断言 `listPublic` 是否可见。**禁止直接 insert approved 夹具**。

## 3. 严重问题（R1）

### R1-1 `verify-contract.js` 绕过了它自己声称要覆盖的传输层

`verify-contract.js:150-156` 的 `stubApi()` 直接覆盖 `utils/api.js` 的 `module.exports` 属性，`:226-237` 把 HTTP 响应体用 `Promise.resolve()` 直接交给页面。结果：`fetchWithFallback` / `hasExpected` / `stampSource` / `rememberStatus` **一次都没执行**；页面看到的是后端原始 `{mode:'server'}`，真实运行时是 `stampSource` 后的 `{mode:'live', fellBack, reason}`。通知数据来自 `:173-186` 手插 `reviewStatus:'approved'`，**绕过了 `ndrcNotice → saveNotice → 机器判定` 全链路**——正是上午报告批评 `check-openapi.js` 的做法。`sourceStatus` 被 mock 成固定 `{mode:'live'}`。

**它测不到的已修项**：`api.js` 回落/fellBack 全链路、五页 `.catch` 可达性、`hasExpected` 的「真实但为空」判定、来源文案一致性（只断言 `!!sourceText`）、`expectKeys`、P0-1 详情 `summary`、追加-2 的 trend30 点数、追加-3 的 WXML 隐藏、`_reqSeq` 竞态、生命周期、弹层 WXML/WXSS。断言期望值由被测的同一份 `fmt.sourceLine`/`applyXxx` 推出，且 stub 让 Promise 永不 reject。

**修复**：把 HTTP 响应挂到 `cloud.callFunction` 层（或注入可控 `wx.request`），让页面真走 `fetchWithFallback`；通知改用 `collector.run()` 产出；补回落、空结果、竞态、生命周期用例。`selftest.js` 的 `loadConfig` 只断言 `validate()` 返回值，没断言 `index.js:start()` 真的调用它 —— 把启动校验整段删掉，134 项仍全绿，也建议补一条。

### R1-2 限流在 nginx 反代下退化成「全站共用一个桶」

`app.js:49` 先取 `req.ip`（永远有值），XFF 分支永不执行；`createApp()` 从未 `app.set('trust proxy', ...)`；`oil-trend.nginx.conf:42` 是 `proxy_pass http://127.0.0.1:3002`。因此**所有用户的 `req.ip` 都是 `127.0.0.1`**，登录 20/分、定位 30/分、rules/history 60/分是全局额度。任一用户或脚本打满，全站 429 —— 比「绕过限流」更严重，是 DoS 放大。XFF 伪造倒是绕不过（这点反而安全）。另外限流只挂了 4 个前缀，`/api/home`、`/api/trend`、`/api/notices`、`/api/market` 完全没挂，`/api/trend` 一次查 3 张表可刷连接池。

**修复**：按部署拓扑设 `app.set('trust proxy', 1)` 并限定可信代理层，或显式取 nginx 追加的 XFF 最右一跳作 key；给查库重接口补限流；`/health`、`/ready` 已注册在限流之前（这点是对的，CI 探活不会被误伤）。

### R1-3 首页「最新调价通知」在数据缺失时仍是空壳卡片

报告头部已诚实承认「ndrc 来源未启用、线上仍无正式调价通知产出」，即后端 `getLatestNotice()` 恒 null。此时 `index.js:339` 的 `latest={}`，`index.wxml:114-126` 渲染出：日期 `--`、**空白标题**、「92# 汽油 调价幅度待公布 · 查看通知详情」，且可点开空白详情弹层，来源「未标注来源」。0.00 换成了 `--`，但卡片仍是空壳。这不是代码回归，是**接通来源前就该有的空态**。

**修复**：`latest` 为空时给 `notice.empty=true`，WXML 显示「暂无正式调价通知」并隐藏日期块与详情入口；详情文案优先用 `latest.summary`（目前 `index.js:399-417` 没带 `summary`，只有调价页用了）。

### R1-4 `/api/*` 错误一律以 HTTP 200 返回（本轮新引入）

`routes/api.js:36` 的 `handle().catch()` 是 `res.json(errors.publicError(err))`，不设状态码；`routes/auth.js:28` 同理。任何 `INVALID_REGION`、DB 故障都返回 `200 + {ok:false}`。外壳统一是好事，但 nginx / 云监控 / CI 无法按 5xx 识别故障，报警与重试策略失效，可观测性归零。

**修复**：白名单业务错误用 4xx，内部/DB 错误用 5xx，保留 `ok/message/code` 外壳；同步核对 `cloud.js` 的 401 判断与 `check-openapi.js` 断言。

### R1-5 去重占位导致失败事件永久不重试

`dao/index.js:589-608` 的 `reserve()` 插一条 `sent=FALSE, fail_reason=NULL` 占住唯一键；`alert.js:248-274` 发送后 `markResult()` 回填，但**失败也保留占位行**，下一轮 `reserve()` 因唯一键冲突恒返回 `null`（`:246` 直接换下一条）。对网络抖动、45009 频率限制这类**可重试**失败，该事件被永久跳过。这沿用了旧代码「失败也记、不重试」的语义，不算回归，但与 R0-1 叠加后是「全失败 → 全占位 → 永不重发」的锁死。

另外 `listByUser` 不过滤未回填的占位行，用户会在提醒历史里看到「发送失败 · 未知原因」。

**修复**：可重试失败删除占位行或写 `retry_at` 并在 `run()` 里捞回；不可重试失败（43101/模板非法）显式 `consumeSubscribe` 并统一标记；`listByUser` 过滤未回填行。

> **风险窗口**：R0-1/R0-2/R1-5 目前线上都未触发（ndrc 未启用、模板未配），所以「全绿」是真的。**但一旦启用来源或配好模板，第一批结果会全错且不可自愈**。建议把这三列为启用前的硬门槛。
