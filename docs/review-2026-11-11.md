## 四、P0 详解

### P0-1 演示日期平移的时间基准混用

- **位置**：`utils/demo-clock.js:12-29,31-39`、`data/demo.js:91-113,128-151,174-177`；数据源 `data/adjustments.js:10-35`、`data/notices.js:9-18,95-100`。
- **现象**：`clock.shiftDate()` 把窗口日期、通知时间、同步时间按「今天 − 锚点」平移，`clock.today()`、`monthsAgo()`、`daysAgo()` 也都基于平移后的今天；但 `levels()` 直接使用 `ADJUSTMENTS` 的**原始日期**，从未平移。于是「已平移的区间起点」与「未平移的调价节点」在同一函数里比较（`periodLevels` 的 `item.date <= fromDate`），事件被逐月过滤掉。
- **另外两处独立错误**：`getHome` 的标签写成 `shiftDate(daysAgo(29))`，`daysAgo` 已平移过，二次平移；`windowPayload` 的 `daysLeft` 传原始日期算，界面却显示平移后的日期，天生差一天。
- **实测退化**（伪造系统时间，完整输出见第六节）：

  | 相对今天 | 3m 点数 / 调价次数 | 窗口日期 | 剩余天数 | 进度 | 首页 30 天首标签 |
  | --- | --- | --- | --- | --- | --- |
  | +0 | 7 / 6 | 2026-11-25 | 13 | 0% | 10月14日 |
  | +30 | 4 / 3 | 2026-12-25 | **-17** | **100%** | 12月13日 |
  | +60 | 3 / 2 | 2027-01-24 | -47 | 100% | 02月11日（未来） |
  | +120 | **1 / 0** | 2027-03-25 | -107 | 100% | 06月11日 |
  | +240 | **1 / 0** | 2027-07-23 | -227 | 100% | 02月06日 |

- **影响**：4 个月后国内走势图变成一条平线、调价次数显示 0；「最近调价日」永远停在 2026-11-02；同步时间固定 18:20，上午打开是未来时间。演示数据「长期打开仍然新鲜」的目标完全失效。
- **建议**：确定**唯一时间基准**——要么整套数据（含 `ADJUSTMENTS`）统一平移后再参与计算，要么全部保留原始日期、只在展示层平移。推荐前者：在 `levels()` 里对 `item.date` 做 `clock.shiftDate()`，并让 `daysUntil()` 接收平移后的日期；删掉 `getHome` 标签里的二次 `shiftDate`。同时给 `verify-data.js` 加一组「模拟未来 N 天」的断言，防止回归。

### P0-2 偏好设置互相覆盖

- **位置**：`utils/store.js:39-47`。`getPrefs()` 的结果赋给了局部变量 `prefs`，之后完全没用；`next` 只复制 `patch` 的键，直接整体写回。

### P0-3 两端共享规则不是同一套

- **位置**：`cloudfunctions/_shared/shared.js:34-39` 只有 4 条调价且为**新→旧倒序**；`data/adjustments.js:10-35` 有 24 条且为**旧→新正序**。`scripts/sync-cloud-shared.js:28-32` 只把 `_shared` 复制到三个云函数目录，**不校验与小程序端一致**（四个副本 md5 确实一致，但内容本身另起炉灶）。

## 五、P1 详解

- **P1-1 / P1-2 数据联动**：`notice.js:42-43` 与 `global.js:28-29` 的 `onShow` 是空函数，换地区后不重取、切回国际页时行情时间停滞（页面里的 `quoteTime` 是取数时生成的固定值）；`trend.js:39-46` 只比对 `fuelId`。建议五个页面统一用一个「比对 prefs 快照 + 数据过期时间」的 `onShow` 逻辑，并给国际页加按时间自动刷新。**同时补上下拉刷新**（全项目没有 `onPullDownRefresh` / `enablePullDownRefresh`）。
- **P1-3 重复请求**：`index.js:41-55`、`alert.js:44-50` 在 `onLoad` 发起异步请求后，紧接着的 `onShow` 因为 `region.code` / `fuelId` 尚未赋值而再发一轮；提醒页因此首屏 3 个接口 ×2。建议加 `_loadingPromise` 去重，或在 `onLoad` 里同步写入初始 `region`/`fuelId`。
- **P1-4 契约不一致**：`index.js:60` 调 `api.getHome(regionCode)`，而 `api.js:58` 与 `oilApi.actionHome` 都接收 `fuelId`。演示源忽略第二参数所以没暴露，云端会拿到 `undefined` 后回退 `'92'`。建议首页按契约传全参数。
- **P1-5 文案反了**：`alert.js:127-129`，`diff = 当前价 − 目标价`，`diff >= 0` 时文案却是「低于目标价 X 元时提醒」。当前价 7.36、目标价 7.20 时应为「再降 0.16 元时提醒」。
- **P1-6 窗口计算**：`data/demo.js:97` 的 `totalDays = daysUntil(cycleStart) − daysUntil(windowDate)` 符号写反，导致 `Math.max(1, 负数)` 恒为 1，进度今天恒 0%、之后跳 100%；`daysLeft` 用未平移日期算，与界面平移后的日期差一天（`verify-data.js` 已能看出「窗口 11-25 / 剩 13 天」）。
- **P1-7 历史价格失真**：`data/demo.js:302-314` 的 `buildPricesFor` 对每条历史通知都用 `currentPrice` 作为「调价后」价；`oilApi/index.js:282` 的 `events.priceAfter` 取 `priceMap[fuelId]`（当前价）。所有历史节点显示同一个价格。
- **P1-8 国际行情周期**：`data/demo.js:345-348` 不管 1日/1周/1月/3月，都按 `(points-1-i) * 60000` 的**分钟**间隔造点，切周期只是点数变化；`oilApi/index.js:328-358` 完全忽略 `payload.period`，`points` 始终返回 `doc.series`，且 `axis` 返回完整日期时间串，而 `global.wxml:57` 直接 `{{item}}` 渲染（演示源返回的是 `HH:mm`）→ 云端模式轴标签撑爆布局。建议统一 `axis` 为短格式，并让周期真正影响取数范围。
- **P1-9 重复云调用**：`global.js:34-38` 的 `Promise.all` 同时请求 `getMarket(symbol)`、`getMarket('brent')`、`getMarket('wti')`，选中某个品种时必有一次是完全重复的，占 1/3 请求量。建议去重后并发，或把两个 tab 的报价合并进一次云函数返回。
- **P1-10 容错**：`api.js:30-46` 把云端返回的**任意 object** 当作成功，`{}` 会让首页拿到空 `prices` 后显示空白而非报错；`cloud.js:45-67` 的 `wx.cloud.callFunction` 没有超时，网络挂起时 loading 永不结束；`notice.js:74` 的 `n.executeAt.slice(...)`、`trend.js:85` 的 `e.amount.toFixed(2)` 在字段缺失时会抛错并中断整个 `setData`。建议加业务字段校验、超时包装和可选字段兜底。

## 七、P2 详解（接真实数据前必须清）

- **P2-1 / P2-2 采集真实性**：`sources.js:52-74` 的 `ndrcNotice` 正则只捕获一个数值且不带符号，`Number(m[1])` 恒为正；公告写「下调 0.08 元」会得到 `delta = +0.08`。`oilCollector/index.js:121` 再把这个值复制给 92/95/98/0 四个油品（真实调价各油品幅度本就不同），并以 `kind: 'official'` 直接入库、由 `oilApi.actionNotices` 返回给所有用户。`summary` 虽写了「正式发布前需人工复核」，但没有任何复核状态字段，前端也无区分。这与「绝不把猜测值发布成正式结果」的硬约束冲突。另外 `executeAt` 只取 `YYYY-MM-DD`，而 seed 写入的是带时间后缀的字符串，混在一起会让 `orderBy('executeAt','desc')` 排序失真。建议：解析按油品分别取幅度、保留下调符号、加 `reviewStatus` 字段，只有 `approved` 才对外可见。
- **P2-3 假装同步**：见 P0-4。`collect()` 应把「全部 skipped / 部分失败」区分为独立状态，`oilApi` 无运行记录时也不应兜底 `ok`。
- **P2-4 seed 防护**：`oilCollector/index.js:161-267` 里 `remove({})` 清空 `oil_prices`、`oil_price_history`、`oil_adjust_events`、`oil_notices`、`oil_windows`、`oil_markets` 后重建演示数据，无环境判断、无二次确认。生产环境误触发 `{"action":"seed"}` 会清空真实数据。建议加显式开关（如仅在特定环境或非生产集合为空时允许），或把 seed 拆成独立脚本不进线上云函数。
- **P2-5 / P2-6 分页**：按微信云开发的平台限制，云函数端单次 `get()` 取数有上限（需在云端实测确认具体值）；`oilApi/index.js:107` 的 `limit(400)` 不会取到 400 条，且 `orderBy('date','asc')` 取到的是**最早的**一批，1 年走势的 `last` 不是当前价。`oilAlert/index.js:183` 的 `db.collection('alert_rules').get()` 无分页，规则数超上限后后面的用户收不到提醒。建议按日期区间分段查询 + 分页遍历，并让走势终点以 `oil_prices` 当前价为准。
- **P2-7 / P2-8 / P2-9 订阅链路**：`subscribeGranted` 是本地永久布尔值，不反映微信一次性订阅额度的消耗，页面会一直显示「微信提醒已开启」，而 `oilAlert` 靠 `alert_logs.dedupKey` 去重、无法感知额度耗尽。模板 ID 要同时手工填 `config/index.js:18` 和 `oilAlert/index.js:35-56` 的 `TEMPLATE_FIELDS`，漏填后者时 `sendSubscribe` 直接返回 `TEMPLATE_NOT_CONFIGURED`，链路静默失败。`miniprogramState: 'formal'` 写死，开发版/体验版联调会失败。另外 `sendSubscribe` 的 `fields` 形参未被使用，模板字段映射实际没有生效，接入时需按公众平台模板详情核对。建议把模板 ID 收敛到一处配置、按环境选择 `miniprogramState`、并在下发失败为额度类错误时回写授权状态。
- **P2-10 权限与 AppID**：`app.json:57-61` 声明 `scope.userLocation`，但全项目没有任何定位 API 调用（`store.seedRegionIfNeeded` 注释也说明首版不定位），审核时可能被要求说明；上线前要么实现定位，要么删掉声明。`scripts/preview-qr.js:52-60` 的 `setAppid()` 把真实 AppID 同时写进 `project.config.json`（**入库**）和 `project.private.config.json`（不入库），与脚本自身注释、`README.md:27` 以及历史上处理过的 GitHub 密钥扫描误报约定矛盾。建议只写 private 文件。
- **P2-11 数据库权限**：`docs/deploy.md:40` 建议「仅创建者可读写，或所有用户可读、仅云函数可写」。所有读取都走 `oilApi` 云函数，小程序端并不直连数据库；`alert_rules` / `alert_logs` 含 openid 与用户规则，设成「所有用户可读」会泄露他人数据。建议统一设为「仅管理端 / 云函数可读写」。

## 八、P3 详解

- **P3-1 ES5 约定**：`app.js`、`pages/`、`utils/`、`data/`、`components/`、`cloudfunctions/` 共 26 个文件含 `const` / `let` / 箭头函数 / 模板字符串，与 `AGENTS.md`「运行时代码用 ES5」冲突。工程配置 `libVersion: 3.8.10`、`es6: true`，功能上没有问题。**推荐改文档约定而非全量重写**：重写 26 个文件收益低、回归风险高。
- **P3-2 检查器**：`scripts/lint-wxml.js:245` 只在 `problems.length` 非零时 exit 1，有警告仍返回 0，与「0 错误 0 警告才算过」不符；且绑定校验只看 `{{}}` 的根变量（`{{notice.sourceName}}` 只验证 `notice` 存在），不校验动态图标路径 `/assets/icons/{{icon}}`、WXML 表达式里的 `?.`/箭头函数、`app.json` 的 tabBar 图标是否存在、页面注册与文件是否一一对应。恰好 `docs/verification.md` 里记录过「动态 src 漏 .png」和「WXML 表达式」两类事故。建议补规则并让警告也可配置为失败。
- **P3-3 包体积**：`assets/app-icon/app-icon.png`（512×512，78K）是给公众平台后台上传头像用的，运行时无引用，却未列入 `packOptions.ignore`，会进主包。当前主包估算约 465K（`docs/verification.md` 记录的 186.6KB 是加入该图标之前的数字），离 2MB 还很宽裕，但属于纯浪费。
- **P3-4 设计令牌**：`styles/tokens.wxss` 定义完整，页面 `var(--x)` 用得不错，但 `pages/*/*.wxss` 仍有约 43 处硬编码色值（主要是 `rgba()` 阴影与边框），`index.wxss` 16 处、`alert.wxss` 10 处。
- **P3-5 弹层**：`components/bottom-sheet/index.wxml:1-11` 的遮罩用 `bindtap` 而非 `catchtap`，面板与内容区没有 `catchtouchmove`，弹出时背景可滚动穿透；`wx:if` 直接显隐，无过渡动画。
- **P3-6 图表**：`components/trend-chart/index.js:31-41` 的 `ready()` 与 `observers` 会重复触发 `render()`，每次都做 `createSelectorQuery` + 重设 canvas 尺寸 + `requestAnimationFrame`；多属性连续 `setData` 时产生多帧竞态，`detached` 时也没有取消 rAF。建议合并为一次调度（如 `nextTick` 批量）并记录帧 id。
- **P3-8 依赖**：三个云函数的 `wx-server-sdk` 均为 `~2.6.3`，建议评估升级到当前维护版本后再部署（升级需回归 `cloud.init` / `openapi` / 数据库 API）。
- **P3-9 其他**：`utils/demo-clock.js:25-29` 的 `offsetDays()` 用「本地 00:00 的 epoch」减「UTC 00:00 的 epoch」再 `Math.round`，在 UTC+8 恰好正确，但换到 UTC+13 等时区会偏一天，建议统一用 UTC 日期部分计算；`oilCollector` 每 30 分钟、`oilAlert` 每 10 分钟触发，后者一天 144 次且 `collector_runs` / `alert_logs` 只增不删，建议按实际需要调频并加清理策略。

### 10.4 实施过程中自己踩的坑

改完这批代码后，模拟器里五个页面全部白屏、`Page.getData` 报 `page destroyed`。排查结论：P3 死代码清理时删掉了 `utils/api.js` 里 `saveAlertHistory` 的函数体，却忘了删 `module.exports` 里的同名导出项 —— 模块一被 `require` 就抛 `ReferenceError`，所有页面跟着挂掉。IDE 日志里的 `compile onFileChange` 反而是干扰项，让人一度以为是重编译时序问题。

顺带记一笔 IDE 的坑：开发者工具监听项目根目录下**任意**文件变化就触发重编译，往 `docs/screenshots/` 写截图会把正在跑的页面冲掉。`verify-in-devtools.js` 因此改成先把截图攒在内存、跑完统一落盘。
